# Pulse Tickets

Two-way ticketing marketplace for Ghana: organizers publish events **and** services, buyers pay with
Mobile Money (MTN / Airtel / Telecel), the platform takes a configurable commission, and every ticket is
a single-use QR pass validated server-side at the gate.

Stack: Laravel 13 · PHP 8.3+ · Blade + Tailwind Play CDN (no Node build step) · SQLite (Postgres-ready) · Docker on Render.

## 2. Deploy to Render (Blueprint, ~10 minutes)

1. **Push the code.** The app lives in `ticketing/`. Create a new GitHub repo and push that folder as the
   repository root (not a subfolder):

   ```bash
   cd ticketing
   git init
   git add -A
   git commit -m "Pulse Tickets marketplace"
   git remote add origin git@github.com:<you>/pulsetickets.git
   git push -u origin main
   ```

2. **Create the Blueprint.** In Render: *New → Blueprint* → select the repo. Render reads `render.yaml`
   and creates the web service (Docker runtime, `starter` plan, 1 GB disk mounted at `/var/data`) with the
   SQLite database file at `/var/data/database.sqlite`.

3. **Fill the `sync: false` values** in the Render dashboard (Environment):

   | Key                     | Value                                   |
   |-------------------------|-----------------------------------------|
   | `APP_KEY`               | `php artisan key:generate --show`       |
   | `APP_URL`               | `https://pulsetickets.onrender.com`     |
   | `PAYSTACK_SECRET_KEY`   | `sk_live_…` (or leave empty for demo mode) |
   | `PAYSTACK_PUBLIC_KEY`   | `pk_live_…`                             |
   | `PAYSTACK_WEBHOOK_URL`  | `https://pulsetickets.onrender.com/api/v1/momo/webhook` |

   `APP_KEY` can also be generated by the container: the entrypoint runs `key:generate` when it is empty,
   but that value is not persisted — set it explicitly.

4. **Point the Paystack webhook** at `https://<your-app>/api/v1/momo/webhook` and subscribe it to
   `charge.success`. The endpoint verifies the signature, is idempotent (`webhook_events`) and checks that
   the amount matches the order.

5. **Seed the first accounts.** Open the Render *Shell* tab:

   ```bash
   php artisan db:seed --force
   ```

   The demo event (`/events/neon-nights-vol-3`) and the three accounts above are created. Then sign in and
   change the admin password.

6. Verify: `https://<your-app>/up` must return 200, and `https://<your-app>/` must render the landing page.

### Switching to Postgres (optional, env-only)

Set `DB_CONNECTION=pgsql` plus `DB_HOST` / `DB_PORT` / `DB_DATABASE` / `DB_USERNAME` / `DB_PASSWORD`, or
attach a Render Postgres and use its `DATABASE_URL`. Nothing in the application code changes; no query
uses a SQLite-only construct.

### Deploy hygiene

- `docker/entrypoint.sh` runs `package:discover`, `migrate --force`, `storage:link`, `config:cache` and
  `route:cache` on every boot.
- `CACHE_STORE=database` and `SESSION_DRIVER=database` are required — the settings cache and the hold
  sweep lock live in the database.
- The SQLite file lives on the Render disk, so it survives restarts and deploys.

## 3. How the money works

All amounts are **integer pesewas** (GHS 120.00 = `12000`).

| Step | Where |
|------|-------|
| Commission resolution | Organizer override → global `platform_commission_bps` → snapshot on the order as `commission_bps_applied` |
| Split at capture | `App\Services\PaymentProcessor::markPaid()` credits the organizer wallet (80% of GHS 120) and books a `fee` ledger row (20% = GHS 24) |
| Refund | `App\Services\RefundService` reverses the organizer's share **and** the commission proportionally, and voids the tickets |
| Payout | Organizer requests → admin settles in `/admin` → `payout` debit row + `payouts` record |

Ledger tables: `wallets`, `wallet_transactions` (`sale`, `fee`, `refund`, `payout`, `adjustment`), `payouts`.

### Changing the commission

`/admin` → **Platform commission** panel. The percentage is always prompted before it is saved
(quick-set buttons for 5 / 10 / 15 / 20). It applies to **new** sales only — in-flight orders keep the
`commission_bps_applied` snapshot. A per-organizer override can be set in `/admin/approvals`.

## 4. Oversell protection

`App\Services\Inventory` never reads-then-writes capacity. It issues a conditional atomic update:

```sql
UPDATE ticket_types
SET held_count = held_count + :qty
WHERE id = :id AND capacity - sold_count - held_count >= :qty
```

Zero affected rows = sold out. On MySQL/Postgres the same path runs inside a `DB::transaction` with
`lockForUpdate()`. Pending orders hold inventory for 10 minutes (`HOLD_MINUTES`); expired holds are swept
lazily on the next request (Render has no cron), guarded by a cache lock.

---

## 5. Ticket lifecycle

1. Payment capture issues one ticket per seat with a unique `qr_code_hash` and a `TKT-XXXX` code.
2. `/organizer/scanner` validates the hash **server-side** (the QR image is never trusted) and returns
   `valid`, `already_used`, `refunded`, `void`, `wrong_event` or `invalid`. Every attempt is written to
   `ticket_scans`.
3. The scanner also supports camera scanning through `html5-qrcode`; pasting the code works offline.

## 6. Swapping the payment gateway

`App\Services\PaymentGateway\Contracts\MomoGateway` is the only contract the checkout touches:

```php
public function initialize(Order $order, array $context): GatewayResult;
public function approve(string $txRef): void;
public function verify(string $txRef): ?GatewayResult;
```

Implement it for Hubtel or Expresspay, then swap the binding in `App\Providers\AppServiceProvider::register()`.
`PaystackMomoGateway` (live) and `DemoMomoGateway` (local) ship with the app.

## 8. Legacy DocuDrop app

The DocuDrop PHP app in the repository root is a **separate, permanent application** and is untouched by
this build. Its hardening track (rotate the live DB password, remove uploaded PHP/HTML, add a
`download.php` gate plus `.htaccess`, CSRF protection, IDOR/XSS fixes, and stopping `sw.js` from
precaching authenticated pages) is a separate piece of work — do not merge it into this codebase.
